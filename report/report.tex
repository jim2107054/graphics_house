\section*{Abstract}\addcontentsline{toc}{section}{Abstract}
This report documents the implementation of \emph{Horror House at Night}, an interactive three-dimensional Gothic environment programmed in C++17 using legacy OpenGL, GLU, and FreeGLUT. The application constructs a large haunted house with explorable ground- and upper-floor interiors, a surrounding graveyard, a rusted automobile, procedural terrain, vegetation, atmospheric clouds, animated animals, and decorative props. The implementation combines geometric primitives, matrix transformations, textured material surfaces, OpenGL fixed-function ambient--diffuse--specular lighting, multiple moving and stationary light sources, planar projected shadows using stencil processing, keyboard and mouse navigation, and time-dependent animation. The central contribution of the project is the integration of these graphics concepts into one coherent real-time interactive scene. Technical discussion in the following chapters is derived primarily from the supplied source files; material in the separate sample report is used as a reference for academic report organization, not as evidence that any feature exists in this project.

\section{Introduction}
Computer graphics converts geometric descriptions of a virtual world into a visible image. This project is designed as an explorable nocturnal environment rather than a set of unrelated graphics demonstrations. The house, surrounding cemetery, vehicle, clouds, weather, materials, lighting, shadows, and moving creatures form a continuous scene that can be observed from multiple locations. The code uses the OpenGL compatibility/fixed-function API: geometry is submitted using immediate-mode primitives such as \texttt{glBegin}, and lighting and material behavior are configured using \texttt{glLight*}, \texttt{glMaterial*}, and related OpenGL state calls. This distinction matters: a Phong-style reflection model is used by fixed-function lighting, but this codebase does not implement a separate GLSL per-pixel Phong shader.

\subsection{Motivation and objectives}
The primary aim is to demonstrate modeling, hierarchical placement, rasterization, illumination, texture mapping, camera transformation, animation and user interaction within one understandable project. Detailed architecture allows examination of how simple cubes, cylinders, spheres, polygons and custom meshes are transformed into recognizable artifacts. Multiple lights demonstrate different spatial emission models, while dark textures, geometry and atmospheric changes create the required horror atmosphere.

\subsection{Project scope}
The scene contains a rotated and translated multi-floor house with a porch and doorway; a decorated parlor and an upper bedroom/study; a fifteen-step staircase; an exterior path and non-flat ground; cemetery headstones and fences; a damaged vehicle; trees, foliage and loose objects; pumpkins; moving bats, a black cat and an owl; celestial sky elements and clouds; a swaying bulb; lightning; audio interface hooks; screenshot capture; a title screen, HUD and cinematic camera route. Each of these items is discussed in the relevant chapters rather than merely named.

\subsection{Implementation status and verification method}
All concrete implementation claims in this report have been checked against the supplied C++ source tree. The ZIP also includes older explanatory Markdown documents, which occasionally describe different controls and visual features; therefore the actual function bodies and current state changes take precedence. \subsection{Frame processing pipeline}
The idle callback obtains elapsed milliseconds from FreeGLUT, converts to seconds and clamps the frame delta to at most $0.1\,\mathrm{s}$. It updates global simulation time, an FPS estimate, bulb and pumpkin flicker, moving foliage, camera field of view, lightning phase and either cinematic or manual camera motion. It then schedules redisplay. The display callback clears color/depth/stencil buffers, selects either the title UI or the 3D perspective, applies \texttt{gluLookAt}, renders lights and scene objects, draws projected shadows and the HUD, and finally swaps buffers.

\subsection{Dependency and source ownership notes}
\texttt{stb\_image} reads external texture images, while GLU provides perspective and camera helper functions. Object construction relies on reusable functions in \texttt{Primitives.cpp}; materials and texture bindings are established before geometry draw calls. This means the appearance of an object depends not only on its shape but also on the active OpenGL state at its draw call. Matrix-stack push/pop and attribute-state restoration are therefore recurring implementation patterns.

\section{Coordinate Systems and Geometric Transformations}
A three-dimensional model is easier to construct in a local coordinate frame and then place in the world using translation, rotation and scaling. The same matrix operations position the complete building, individual architectural components, furniture, vegetation and articulated creatures.

\subsection{Homogeneous transformations}
A point $\mathbf p=(x,y,z,1)^T$ is transformed with a $4\times4$ matrix. Translation and scaling are
\begin{equation}T(a,b,c)=\begin{bmatrix}1&0&0&a\\0&1&0&b\\0&0&1&c\\0&0&0&1\end{bmatrix},\qquad S(s_x,s_y,s_z)=\begin{bmatrix}s_x&0&0&0\\0&s_y&0&0\\0&0&s_z&0\\0&0&0&1\end{bmatrix}.\end{equation}
A yaw rotation around the world $y$ axis is
\begin{equation}R_y(\theta)=\begin{bmatrix}\cos\theta&0&\sin\theta&0\\0&1&0&0\\-\sin\theta&0&\cos\theta&0\\0&0&0&1\end{bmatrix}.\end{equation}
For a centered box whose local dimensions are $(w,h,d)$, the common modeling expression is $M=T\,R\,S$. Many objects are built by drawing a dimensioned \texttt{drawBox} after a call to \texttt{glTranslatef}, so an additional scaling matrix is not required for that primitive's dimensions. Operations inside \texttt{glPushMatrix}/\texttt{glPopMatrix} do not alter parent placement.

\subsection{Full house transformation}
The source defines $x_h=-2.8$, $z_h=-11.5$ and a yaw of $-18^\circ$. In \texttt{drawHouse}, the code first translates and then rotates, so the house's local geometry is transformed by
\begin{equation}\mathbf p_{world}=T(-2.8,0,-11.5)R_y(-18^\circ)\mathbf p_{local}.\end{equation}
These exact constants also matter for embedded lights, collision coordinates and camera-relative positioning. For example, a local position $(x_l,y_l,z_l)$ becomes
\begin{align}x_w&=-2.8+x_l\cos\theta+z_l\sin\theta,\\y_w&=y_l,\\z_w&=-11.5-x_l\sin\theta+z_l\cos\theta.\end{align}

\figureplaceholder{03_transform_hierarchy.png}{Hierarchical scene graph transformation tree: House parent world translation and yaw with child foundations, walls, roofs, furniture, and windows.}

\subsection{Transform order and the matrix stack}
OpenGL's fixed-function matrix stack makes hierarchical construction possible. The parent building transform is active while its children are rendered. Each child saves the current modelview matrix, applies local translations/rotations/scales, draws a primitive or subassembly and restores the matrix. Reversing multiplication order changes the result: $TR$ rotates an object before relocating it, whereas $RT$ rotates its already translated location around the origin. A rotation around a hinge is constructed as translation to the pivot, rotation, and an appropriate relative geometry offset.

\subsection{World and local conventions}
The environment uses the $y$ axis as vertical. Terrain is sampled at horizontal $(x,z)$ positions, while the camera's yaw angle controls heading across the $xz$ plane. Each house component is authored in house-local coordinates, and the house yaw then aligns that complete structure with the exterior. The same principle is used when placing lights inside the upper floor: local light coordinates are explicitly rotated and translated to world coordinates.

\subsection{Box geometry}
\texttt{drawBox} begins from $(\pm w/2,\pm h/2,\pm d/2)$. Each face is assigned a normal; adjacent faces have different normals because a hard-edged box should not interpolate into a rounded surface. Surface coordinates are generated so the selected image repeats across the corresponding face. Real architectural features are assembled by positioning many such boxes, rather than treating a solid wall as a single uncut volume.

\subsection{Cylinder and conical surfaces}
For $N$ circular samples, the azimuth is $\phi_i=2\pi i/N$. A side vertex at radius $r$ and height $y$ is $\big(r\cos\phi_i,y,r\sin\phi_i\big)$. Varying the radius between the two ends produces a truncated cone. This procedure is reused for tree trunks, rails, shaped furniture legs, candleholders and curved mechanical or decorative details.

\subsection{Spherical and ellipsoidal parts}
With polar/latitude parameter $\alpha$ and longitude $\phi$, one convenient spherical parameterization is $\mathbf p=r(\cos\alpha\cos\phi,\sin\alpha,\cos\alpha\sin\phi)$. The vertex normal for a sphere centered at the origin is $\mathbf n=\mathbf p/r$. A sphere drawn under nonuniform scaling becomes an ellipsoid; the program employs this construction for several rounded and organic parts. \texttt{GL\_NORMALIZE} is enabled to keep transformed normals unit length under scaling.

\subsection{Normals, texture coordinates and surface facets}
OpenGL's lighting calculation depends on a surface normal at the submitted vertices. Triangle normals can be derived from the cross product $\mathbf n=\frac{(\mathbf b-\mathbf a)\times(\mathbf c-\mathbf a)}{\lVert(\mathbf b-\mathbf a)\times(\mathbf c-\mathbf a)\rVert}$. Flat faces may use one constant normal; curved geometry varies normals around its circumference or surface. UV coordinates map each mesh vertex to a location in the chosen bitmap. \texttt{GL\_SMOOTH} enables interpolation of vertex colors across polygons, which is distinct from a custom fragment shader.

\section{Lighting and the Reflection Model}
Lighting is an important course outcome demonstrated directly in the application. The implementation uses OpenGL's fixed-function lighting rather than GLSL shader programs. The light types, positions, falloff settings and scene material coefficients determine the rendered colors. The word ``Phong'' here refers to the ambient--diffuse--specular reflection formulation; smooth vertex interpolation is supplied by OpenGL's Gouraud-style pipeline.

\subsection{Ambient, diffuse, specular and emissive terms}
For an illuminated surface with normal $\hat{\mathbf N}$, light vector $\hat{\mathbf L}$ and view vector $\hat{\mathbf V}$, a conceptual fixed-function lighting expression is
\begin{equation}\mathbf I=\mathbf E+\mathbf k_a\odot\mathbf I_a+\sum_i f_{att,i}f_{spot,i}\left[\mathbf k_d\odot\mathbf I_{d,i}\max(0,\hat{\mathbf N}\cdot\hat{\mathbf L}_i)+\mathbf k_s\odot\mathbf I_{s,i}\max(0,\hat{\mathbf R}_i\cdot\hat{\mathbf V})^n\right].\end{equation}
Here $\mathbf E$ is the emissive contribution, $\odot$ is componentwise multiplication, and $n$ is shininess. The equation describes the reflection model but does not imply a custom pixel shader or physically based renderer.

\subsection{Light-source inventory}
The program uses six explicitly configured OpenGL light IDs, numbered \texttt{GL\_LIGHT0} through \texttt{GL\_LIGHT5}, in addition to decorative emissive/glowing geometry. A positional light has homogeneous coordinate $w=1$, while a directional source uses $w=0$. The ``area light'' is an approximation using one positional source, not an extended emitter integrated over a surface.

\subsection{Distance attenuation}
Point-light falloff follows
\begin{equation}f_{att}(d)=\frac{1}{k_c+k_l d+k_qd^2}.\end{equation}
The parameters are set in \texttt{initOpenGL}. The porch bulb is relatively localized, while the flashlight is bright enough to illuminate a forward cone. Directional moonlight is modeled as rays from infinity and thus does not use distance attenuation.

\subsection{Spotlight direction and cone}
The flashlight position tracks the eye $(x_c,y_c,z_c)$ and its direction is built from camera yaw $\psi$ and pitch $\beta$:
\begin{equation}\hat{\mathbf f}=(\cos\psi\cos\beta,\sin\beta,\sin\psi\cos\beta).\end{equation}
\texttt{glLightfv(GL\_LIGHT2,GL\_SPOT\_DIRECTION,...)} aligns the illumination with the view. With a cone half-angle $\gamma$, the source is active only when the direction-to-fragment lies within the cone; the \texttt{GL\_SPOT\_EXPONENT} parameter influences concentration. The visible beam is drawn separately with translucent geometry and should not be mistaken for true participating-media scattering.

\subsection{Material coefficients and shading implementation}
\texttt{Material.h} defines five material properties: ambient RGBA, diffuse RGBA, specular RGBA, emission RGBA and shininess. \texttt{applyMaterial} uploads them with \texttt{glMaterialfv} and \texttt{glMaterialf}. \texttt{glShadeModel(GL\_SMOOTH)} controls interpolation of vertex lighting. The implementation does not contain a user-written GLSL fragment shader, ray tracer, physically based BRDF or shadow mapping pass. Metallic objects can have stronger highlights through higher specular coefficients and shininess, while unlit surfaces remain dark.

\section{Planar Shadow Projection and Stencil Processing}
Shadows are constructed by projecting geometry onto a ground plane, then using stencil state to control which framebuffer pixels receive darkening. This is a planar projection technique rather than ray tracing or depth-map shadow mapping.

\subsection{Projection matrix derivation}
Represent a plane by $\boldsymbol\pi=(a,b,c,d)^T$ with $ax+by+cz+d=0$ and a light in homogeneous coordinates by $\mathbf L=(L_x,L_y,L_z,L_w)^T$. If $s=\boldsymbol\pi^T\mathbf L$, the homogeneous projection matrix used by the code has the compact form
\begin{equation}S=sI-\mathbf L\boldsymbol\pi^T.\end{equation}
For the horizontal ground, $\boldsymbol\pi=(0,1,0,0)$; substituting the moon direction creates the ground-shadow transform. OpenGL's column-major ordering determines how these sixteen coefficients are assigned in memory.

\subsection{Render passes and stencil logic}
\texttt{renderPlanarShadows} first configures relevant rendering state and uses a transformed set of shadow casters to mark eligible stencil regions without writing their colors. It subsequently blends the visible shadow effect while the stencil test restricts affected pixels. The code uses depth testing and polygon offset to reduce ground z-fighting and duplicate dark bands. A separate caster set supports the porch bulb. Since this is a horizontal planar receiver, these projected silhouettes do not reproduce all self-shadows or shadows on arbitrary vertical surfaces.

\figureplaceholder{14_shadow_passes.png}{Planar shadow projection pipeline: light matrix projection, stencil buffer single-count masking, and blended ambient ground darkening.}

\subsection{Shadow casters and practical limitations}
The caster function draws the house, trees, vintage car, telephone pole, environmental clutter, graves, pumpkins and cloud caster geometry. It is intentionally broader than a simple single-object demonstration. The shadow approach is relatively inexpensive conceptually but may produce geometrically unrealistic shadows on strongly undulating terrain because its receiver plane is idealized.

\section{Texture Mapping and Surface Appearance}
The texturing subsystem binds image/procedurally generated textures through an enum and applies them with the \texttt{GL\_MODULATE} texture environment. Texture maps convey material detail without requiring every grain, stone patch or rust fleck to be separately modeled.

\subsection{Texture classes and identifiers}
The texture enum provides \texttt{TEX\_WALL}, \texttt{TEX\_ROOF}, \texttt{TEX\_GROUND}, \texttt{TEX\_STONE}, \texttt{TEX\_BARK}, \texttt{TEX\_RUST} and \texttt{TEX\_MOON}, plus \texttt{TEX\_NONE}. The loader tries candidate image files in the \texttt{textures/} folder. When available textures cannot be read, the code can synthesize RGBA pixel arrays and upload a procedural alternative, preserving a visible material effect rather than leaving a missing-image artifact.

\subsection{Sampling, mipmaps and modulation}
\texttt{loadSceneTexture} assigns filtering and uses \texttt{gluBuild2DMipmaps}, with minification set to \texttt{GL\_LINEAR\_MIPMAP\_LINEAR}. The applied texture participates in the final vertex color using \texttt{GL\_MODULATE}, i.e.
\begin{equation}\mathbf C_{out}\approx\mathbf C_{lighting}\odot\mathbf C_{texture}.\end{equation}
Pressing \texttt{T} changes the \texttt{g\_texturesEnabled} flag and \texttt{bindTexture} suppresses texture usage when this flag is false. This creates an immediate comparison of geometric/material shading versus textured surfaces.

\subsection{UV coordinate behavior}
Box, roof and sphere drawing functions accept tiling factors or specify UVs, so repeated architectural structures share a stable texel scale instead of stretching one image over an arbitrarily long surface. \section{Terrain Mathematics and Procedural Placement}
The ground height is evaluated from a deterministic mathematical function rather than an imported image heightmap. It is designed to be non-flat away from the important walking areas yet relatively even under the building and path.

\subsection{Height function}
The source computes
\begin{align}h_1&=0.30\sin(0.075x+1.2)\cos(0.065z+0.5),\\h_2&=0.12\sin(0.18x-0.15z)\cos(0.12x+0.20z),\\h_3&=0.05\sin(0.38x+0.32z),\\H(x,z)&=[h_1+h_2+h_3]B_{house}(x,z)B_{path}(x,z).
\end{align}
The house and path attenuation factors are directly implemented in \texttt{getTerrainHeight}. They reduce abrupt height variation around the foundation and road while retaining gentle undulation farther away.

\subsection{Finite-difference normal}
For $\epsilon=0.15$, height derivatives are approximated by central differences. The corresponding normal is
\begin{equation}\mathbf n=\operatorname{normalize}\left(\frac{H(x-\epsilon,z)-H(x+\epsilon,z)}{2\epsilon},1,\frac{H(x,z-\epsilon)-H(x,z+\epsilon)}{2\epsilon}\right).\end{equation}
This supplies continuous-looking diffuse illumination over triangles built from the height function.

\subsection{Road centerline and smoothstep}
The visible entrance path uses a separate horizontal centerline, smoothly changing with $z$. The function uses $t=\operatorname{clamp}((22-z)/25.5,0,1)$ and cubic $s(t)=3t^2-2t^3$ to blend from one offset to another, with a sinusoidal sideward bend. Smoothstep has zero first derivative at both ends, avoiding a visible kink at the interpolation boundaries.

\section{Animation and Temporal Effects}
The simulation uses the elapsed wall-clock time and clamped frame delta to animate both continuous motion and occasional events. Unlike frame-index increments, an update proportional to $\Delta t$ better preserves motion speed across different frame rates.

\subsection{Hanging bulb sway}
The bulb uses two angular oscillations,
\begin{equation}\theta_x(t)=14^\circ\sin(2.1t),\qquad\theta_z(t)=6^\circ\cos(1.6t).\end{equation}
Given beam anchor $(x_b,y_b,z_b)$ and cord length $\ell$, the source computes displaced coordinates such as $x=x_b+\ell\sin\theta_z$ and $y=y_b-\ell\cos\theta_x\cos\theta_z$. The bulb geometry and \texttt{GL\_LIGHT0} are drawn/placed using the resulting world position, so the illumination follows the swinging lamp.

\subsection{Bulb and candle flicker}
The bulb brightness combines a constant base, a product of sine and cosine functions, and a small random component. Occasional sharp dimming creates a distressed-light effect. Pumpkins use $f_p(t)=0.85+0.15\sin(4.5t)\cos(2.8t)$. Upper-floor candle and lantern intensities use their own trigonometric modulation in the main renderer. These are visual lighting controls rather than fluid or electromagnetic simulations.

\subsection{Lightning state machine}
\texttt{triggerLightning} resets a timed event, assigns a strike duration and a future interval, and schedules a thunder-related flag. During subsequent idle frames the intensity follows successive flash pulses: a short rise, dip, main flash, short recovery, secondary flash and decay. The global ambient term, sky clear color and directional-light values use this intensity, providing synchronized atmospheric flashes. The code schedules spontaneous strikes after randomized intervals and also supports manual triggering with \texttt{L}.

\subsection{Moving clouds, leaves and bats}
Clouds use constant-speed horizontal drift and modulo wrapping; an individual cloud has $x(t)=\operatorname{wrap}(x_0+vt)$ and $y(t)=y_0+A\sin(\omega t+\phi)$. Leaves have per-particle update functions and custom mesh rendering. Bat animations change body placement and membrane-wing flap geometry over time. These animations are procedural rather than skeletal animation imported from a 3D asset package.

\section{Camera, Perspective, Collision and Navigation}
Interactive movement is implemented through a first-person camera with position, yaw, pitch and a field-of-view state. A second, automated cinematic controller follows predetermined key views for a demonstration tour.

\subsection{Viewing direction}
Using yaw $\psi$ and pitch $\beta$, the normalized forward vector is
\begin{equation}\mathbf f=(\cos\psi\cos\beta,\sin\beta,\sin\psi\cos\beta).\end{equation}
The target sent to \texttt{gluLookAt} is $\mathbf c+\mathbf f$, with world up $(0,1,0)$. The projection is \texttt{gluPerspective(FOV, width/height, 0.2, 350.0)}, configured anew for the 3D scene.

\subsection{Keyboard and mouse input}
Key press/release callbacks maintain input state; the camera update consumes it using delta-time. Mouse motion changes yaw/pitch, and pitch is clamped to the range $[-85^\circ,85^\circ]$. Scrolling changes the target FOV; per-frame smoothing applies $F\leftarrow F+(F_{target}-F)\min(1,14\Delta t)$, producing a responsive but gradual zoom. Vertical movement is also available in free-camera controls.

\subsection{House and terrain navigation}
\texttt{Camera.cpp} contains explicit checks against the transformed house footprint and room boundaries rather than relying on an external physics engine. World coordinates are converted into house-local coordinates for collision decisions. Doorway and staircase logic allow movement between intended walkable spaces. Outdoor movement consults the terrain height function for ground-relative behavior. The full collision logic should be tested from representative boundary approaches before publishing screenshots.

\subsection{Cinematic tour}
\texttt{Camera.cpp} defines a 90-second repeating tour using a sequence of key views, with timed demonstrations that toggle lighting or materials. It also includes programmed lightning, a flashlight demonstration, and other changes at scheduled seconds. Although an older README states a shorter eight-stage tour, the current source constant is \texttt{TOTAL\_TOUR\_DURATION = 90.0f}, and the present implementation is authoritative.

\section{Rendering Sequence and OpenGL State Management}
The final frame is not produced by independent image files for each object. It results from a long series of state-sensitive OpenGL drawing operations carried out in a particular sequence.

\subsection{Scene composition order}
The main scene function first updates global ambient and individual light sources. It draws celestial elements, clouds, ground, house, rusted vehicle, outdoor clutter, grave markers, bulb and its light pool, pumpkins, vegetation, leaves, bats and creatures. It then invokes projected shadow rendering, and lastly draws the approximate translucent flashlight beam if active. Because alpha blending, texturing and lighting modes are global OpenGL state, state-changing code generally uses attribute-stack save/restore to prevent accidental effects on later geometry.

\subsection{Depth, double buffering and normal correction}
The renderer enables depth testing with \texttt{GL\_LEQUAL} and normal normalization. It clears color, depth and stencil attachments before each scene. Double buffering allows the completed back-buffer image to be presented using \texttt{glutSwapBuffers}, helping avoid visible partial redraw. Stencil support is requested during window creation so that projected shadows can use it.

\subsection{Transparency and blend modes}
Transparent windows, ground-light halos and approximate volumetric light employ blending with appropriate state changes. Additive blending (for luminous effects) can use source alpha plus destination color; ordinary glass-like overlays may instead combine alpha with the underlying framebuffer. Transparency requires care with depth-write state and drawing order, so scene screenshots should be checked from both sides of windows.

\section{Limitations and Possible Improvements}
The project has broad geometric and interaction scope, but its chosen OpenGL rendering architecture imposes clear technical boundaries. Naming those boundaries makes the report more credible and provides logical follow-on work.

\subsection{Limitations established by source inspection}
The renderer relies on the compatibility fixed-function pipeline and immediate-mode geometry, which can be less efficient than indexed VBO/VAO rendering for complex scenes. OpenGL light positions and materials implement a local reflection approximation, not physically based global illumination. The ``area'' window light is a point approximation. Ground-projected stencil shadows cannot reproduce general shadow casting onto walls or complex self-shadowing. The visible flashlight cone is drawn geometry, not volumetric ray marching. Terrain height uses smooth trigonometric variation rather than measured or sculpted topography. Fog is actively disabled in the current implementation, and puddle functions are empty. Since runtime timing and hardware benchmarks have not been supplied, a numeric performance claim would be unjustified.

\subsection{Future work}
Possible extensions include upgrading to modern programmable OpenGL with GPU buffers and shaders, adding shadow mapping for self-shadowing and arbitrary receiving geometry, using physically based roughness/metallic materials, replacing approximate area lighting with sampled or shader-based extended emitters, providing user-selectable atmospheric fog, improving alpha sorting, implementing an optional collision visualization mode, introducing LOD/instancing for vegetation and compiling a reproducible frame-time benchmark across test camera locations. These are recommendations, not existing verified project functions.

\section{Conclusion}
\emph{Horror House at Night} demonstrates an integrated computer graphics environment built by constructing objects from geometric primitives and applying hierarchical transformations, textured materials, fixed-function lighting, camera projection and procedural animation. The building's local-to-world placement is mathematically explicit; the scene's decorative geometry is concentrated in well-defined modules; the world is grounded by a continuous terrain-height function; the atmosphere is created through lamps, moonlight, lightning, clouds and animated creatures; and the user can explore the scene and toggle key rendering features. Planar stencil shadows and scene-specific collision logic provide additional graphics and interaction depth. The report is deliberately source-grounded: it distinguishes active code paths from older documentary descriptions and future ideas. Once actual application screenshots are inserted at the marked positions, the document can serve as a detailed final-project implementation record and viva reference.
